# Atlassian

- The Atlassian agent handles everything Atlassian: Jira, Confluence, and any other Atlassian product the plugin reaches. "Atlassian work" below means reading or writing any of them.
- Whenever a task involves Atlassian work, such as a Jira ticket ID or URL, a Confluence page or space, or an Atlassian search, use exactly one sub-agent named "Atlassian" running the latest Claude Sonnet model on the `~/.claude` work account. Only that account has the user's Atlassian access. Route all Atlassian work through it. In T3 Code, delegate it through T3 Code to the Claude provider instance pinned to `~/.claude` (Office); in Claude Code run directly from `~/.claude`, use Claude Code's native sub-agent tools.
- The Atlassian agent reaches Atlassian only through the Atlassian plugin's tools (`mcp__plugin_atlassian_atlassian__*`). Never use the old Atlassian MCP servers (`mcp__atlassian__*`, `mcp__claude_ai_Atlassian__*`), even when they are connected. If the plugin's tools are missing or need sign-in, report that as the Atlassian access blocker.
- Create the Atlassian agent once, retain its handle, and reuse it for every Atlassian read, update, and verification throughout the task and on resume. Do not spawn separate Atlassian sub-agents for individual operations or products.
- The Atlassian agent owns all Atlassian reading and writing. The parent passes it the task context: ticket IDs, page links, goals, progress, decisions, evidence, and links. The agent chooses queries and fields, interprets tickets and pages, drafts updates under the `writing` skill, picks status transitions, and returns concise results to the parent.
- When assigned the Atlassian agent role, do the Atlassian work yourself within these safeguards without spawning another Atlassian agent. Include this role and the safeguards in the agent's instructions.
- Atlassian reads require no approval. Fetch each provided ticket or page at task start and on resume. For a Jira ticket, return its requirements, acceptance criteria, current status, and relevant comments; for a Confluence page, return the content relevant to the task. Return these to the parent before dependent work proceeds.
- Treat EPRDS tickets, identified by the `EPRDS-` key prefix, as read-only. Read their details as needed, but never write to them, including editing fields, adding comments or attachments, or changing status. This restriction overrides the progress-update rules below.
- For everything else, every write needs user approval first, including Jira field edits, comments, attachments, and status transitions, and Confluence page creation, edits, moves, and comments. The Atlassian agent returns the ticket ID or page link and the exact proposed changes to the parent, the parent presents them to the user and relays the answer, and the agent applies only the approved changes. Providing a ticket or page, or approving a different update, does not authorize a write.
- At meaningful milestones, including work starting, scope or decision changes, blockers, implementation, validation, PR creation, and completion, the parent sends the Atlassian agent the new progress, and the agent drafts concise Jira updates with evidence and links for approval.
- Preserve existing requirements and other people's content on tickets and pages. Record only observed progress, avoid duplicate comments, and mark a ticket Done only when its acceptance criteria and required validation are satisfied.
- The Atlassian agent reads back each update and reports what changed. If the Atlassian agent, the Sonnet model, or Atlassian access is unavailable, report the blocker and retain the pending update for retry. Do not switch to another runtime, access Atlassian credentials elsewhere, or claim an unverified update succeeded.
